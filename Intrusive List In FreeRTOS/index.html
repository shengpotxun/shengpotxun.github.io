Intrusive List In FreeRTOS

Created2026-04-27|Updated2026-05-24|TechnologyEmbedded
|Word Count:1.4k|Reading Time:8mins|Post Views:

My goal is to understand the inner workings of the FreeRTOS kernel’s list and task scheduler.

Definition in list.h

First, open the file list.h in \FreeRTOS\Source\include. You will see many macros at the top of the file. You can rewrite all these macros in FreeRTOSConfig.h.

xLIST_ITEM

Let’s examine the most important structure, xLIST_ITEM:

Compare it with a normal doubly linked list node:

  • listFIRST_LIST_ITEM_INTEGRITY_CHECK_VALUE & listSECOND_LIST_ITEM_INTEGRITY_CHECK_VALUE : C structs have strict memory layout rules. We can define these macros as special values. If their values have been changed, it means something accessed the memory incorrectly, and the system should return an error.
  • configLIST_VOLATILE TickType_t xItemValue: This variable stores the priority of a task (in most cases).
  • pxNext & pxPrevious: Just like a normal doubly linked list, they point to the previous node and the next node.
  • pvOwner: This pointer is very important. It points to the TCB (Task Control Block) that owns this list item. When we need to change the state of a TCB, we use this pointer to locate that specific TCB.
  • pxContainer: This pointer points to the head of the list that contains this list item.

Some people may feel confused about pvOwner and pxContainer. Let me give an example:

When we are waiting in a queue, we might unfortunately need to go to the restroom. In that case, you can leave your phone number as a placeholder — this is like pvOwner. Anyone can call you using that number. The pxContainer, on the other hand, tells us which restaurant you are waiting for: KFC or McDonald’s.

xLIST(List_t)

This structure represents the list head (or list control block).

  • configLIST_VOLATILE UBaseType_t uxNumberOfItems – As the name suggests, this stores the number of ListItem_t nodes currently in the list.
  • ListItem_t * configLIST_VOLATILE pxIndex – This is the true core of the structure. It is used to iterate through the doubly linked list.
  • MiniListItem_t xListEnd – A special marker at the end of the list. We use MiniListItem_t instead of a full ListItem_t because the end marker only sits at the end and does not need a priority value.

Operations in list.c

We can find some functions in the list.c

vListInitialize

What vListInitialise does:

  • Creates an empty doubly linked list – the pxIndex is set to point to xListEnd.
  • Ensures the end node xListEnd always stays at the end by giving pxList->xListEnd.xItemValue the maximum possible priority value (portMAX_DELAY).
  • Sets uxNumberOfItems to 0 because the list is empty.

portMAX_DELAY always 0xFFFFFFFF

vListInitialiseItem

Some readers may be confused about this function. We already have vListInitialise, so why do we still need vListInitialiseItem?

First, note the parameter types of these two functions.

  • vListInitialise takes a List_t * (the list head).
  • vListInitialiseItem takes a ListItem_t * – this is the node structure embedded inside a TCB.

So vListInitialiseItem acts as an initializer for a list item that belongs to a task’s TCB. Its job is to set pxContainer (the pointer that points to the list containing this item) to NULL.

Why two different initializer functions?

In an OS, pxReadyTasksLists (the ready lists for all tasks) must be built when the kernel starts. However, new tasks (and their TCBs, which contain ListItem_t nodes) may be created at any time after the system is running. Therefore, we need two separate functions: one to initialize the list head itself, and another to initialize each list item as it is created.

vListInsertEnd

A key fact: the FreeRTOS list is circular. When you insert a new list item before pxIndex, you are guaranteeing that the new item will not be accessed immediately; instead, it will be encountered only on the next iteration of the list traversal — i.e., after pxIndex has advanced.

vListInsert

vListInsertEnd always inserts an item at the end of the list without considering the item’s value.
In contrast, vListInsert inserts an item only after it finds an existing list item whose value is larger than the new item’s value.
Therefore, vListInsert has a time complexity of O(N).

uxListRemove

The key point of this function is the check if ( pxList->pxIndex == pxItemToRemove ). If pxIndex points to the item being removed, the function updates pxIndex to point to the previous item in the list (or to xListEnd if necessary), ensuring the iterator never becomes invalid.
