Embedded C Memory Management

Created2026-04-20|Updated2026-04-23|TechnologyEmbedded
|Word Count:718|Reading Time:4mins|Post Views:

Typical Memory Map

In an embedded MCU, the layout usually contends five segments:

  • Text Segment
  • Data Segment
  • BSS
  • The Stack
  • The Heap

Text Segment(code)

The Text segment contains the executable instructions of your program.

  • Location: Usually stored in Flash Memory (ROM) because it is non-volatile.
  • Characteristics: It is typically read-only to prevent the program from accidentally modifying its own instructions.
  • Content: Your compiled C functions and constant data (like hardcoded strings).

If you have not forget the PC(Program Counter), you might find the key point that PC always points the address of next order. In another way, it always points text segment.

Data Segment(GVAR/Initialized)

Data segment stores globle, static variables that have been explicitly initialized by the programer.

  • Location: It occupies space in Flash (to store the initial value) and RAM (where it is copied during startup so it can be modified).
  • Example: int threshold = 10;
  • Sub-type: Sometimes divided into “Read-Only Data” (RODATA) for const variables.

BSS Segment (Uninitialized)

BSS stands for “Block Started by Symbol.” It contains global and static variables that are not initialized in the source code or are initialized to zero.

  • Location: RAM.
  • Characteristics: The startup code (CRT0) clears this memory block to zero before main() is called. This saves space in Flash because you don’t need to store a thousand zeros; you just store the size of the block.
  • Example: static int sensor_buffer[100];

If a glabal variable is initialized in 0, it will be stored in BSS instead of Data

The Stack

The Stack is a “Last-In, First-Out” (LIFO) structure used for dynamic execution management.

  • Location: RAM.
  • Content: Local variables, function return addresses, and function parameters.
  • Management: Handled automatically by the CPU/Compiler. It grows and shrinks as functions are called and return.
  • Embedded Risk: Stack Overflow. If you have deep recursion or massive local arrays, the stack can collide with the Heap or BSS, causing a system crash.

The Heap

The Heap is used for Dynamic Memory Allocation (malloc, calloc, free).

  • Location: RAM.
  • Management: Handled manually by the programmer.
  • Embedded Note: In many high-reliability embedded systems (like automotive or medical), the use of the Heap is forbidden or strictly limited to initialization. This prevents memory fragmentation, where memory is “available” but broken into tiny, unusable pieces.

Stack and heap start at opposite ends of the available RAM and grow towards each other.

  • The Heap starts at a lower address and grows UP (towards higher addresses).
  • The Stack starts at the highest address and grows DOWN (towards lower addresses).

Dangling Pointer & Memory Leak

A pointer that is not initialized or points to a illegal address.This leads to Segmentation Fault.Usually this is not a very hard problem to avoid.But the siquation below is a completely disaster.

In FreeRTOS, every task has a private stack, but when it uses malloc, it will be allocated a block of memory in heap. There is a Task A which have owned a block of memory in heap, and it sends a pointer to task B through Message Queue, but Task A is deleted unexpectedly, will this lead to some problems?

In this case, it will not cause an immediate crash, and the pointer is perfectly valid. However, it creates a massive risk for a Memory Leak.

When Task A is suddenly deleted (e.g., it calls vTaskDelete(NULL) or another task kills it), the FreeRTOS kernel cleans up exactly two things:

  1. The Task Control Block (TCB): The struct FreeRTOS uses to manage the task.
  2. The Task’s Private Stack: The memory used for Task A’s local variables is returned to the system.

Crucial Embedded Fact: FreeRTOS does not automatically free heap memory allocated by a deleted task. Unlike Linux or Windows, where the OS forcefully reclaims all memory when a process dies, an RTOS is lightweight. It expects the programmer to manage the heap.

Usually, the task that allocates memory is responsible for freeing it. If Task A was deleted unexpectedly, who is going to call vPortFree() on that pointer?

  • If Task B simply reads the data and discards the pointer, that block of the Heap is permanently marked as “in use.”
  • If this happens repeatedly, your Heap will slowly fill up until a pvPortMalloc() fails, causing the whole system to crash.
